# PRD — 10.2 Mercado Pago Production Readiness & 9B Preparation

**Status:** planned.
**Aggregate branch:** `feature/10.2`.
**Objective:** make Mercado Pago safe for production payments and prepare it as a reliable financial source for 9B Marketplace Settlement.

## 1. Problem

LedgerFlow already has a Mercado Pago payment foundation, but the provider is not yet production-ready end to end. OAuth and basic payment creation exist, while webhook processing, automatic refresh, cancel/refund, E2E validation and settlement-read readiness are incomplete.

Starting 9B settlement before closing those gaps would force reconciliation to rely on partial provider state and assumptions.

## 2. Expected outcome

```text
Mercado Pago OAuth connection
→ encrypted tenant credentials
→ automatic refresh lifecycle
→ PIX/boleto payment create/fetch
→ webhook inbox/outbox
→ status sync and notifications
→ production E2E evidence
→ financial-read readiness
→ 9B settlement ingestion/matching
```

## 3. Scope

### Mercado Pago payment readiness

- Current-state hardening and provider slug normalization.
- Automatic backend-only token refresh with lock/versioning.
- Webhook endpoint, signature validation, inbox/outbox and async processing.
- Payment status sync from provider webhook/fetch data.
- Cancel/refund support where allowed by provider and internal state.
- Production E2E payment runbook and validation evidence.

### 9B preparation

- Reuse `GatewayConfiguration` short-term for settlement-read readiness.
- Separate payment gateway behavior from financial-read/settlement services.
- Add financial health/scope checks.
- Create financial accounts/opening balance.
- Ingest Mercado Pago financial facts into normalized settlement events.
- Match Mercado Livre orders/payments with Mercado Pago financial events.

## 4. Out of scope

- Full card payment support until a secure card architecture is explicitly designed.
- XLSX export in the first settlement slice; CSV async is the accepted first format.
- Official accounting. Cash and P&L views are operational management views.
- Consuming Mercado Pago directly from n8n. n8n must consume sanitized LedgerFlow outbound events only.
- Creating a separate `FinancialIntegrationConnection` in the first iteration unless `GatewayConfiguration` becomes insufficient.

## 5. Personas and permissions

| Persona | Need | Guardrail |
|---|---|---|
| Tenant admin | Connect/reconnect Mercado Pago | OAuth state is tenant/user/provider-bound |
| Finance user | See payment/settlement health | RBAC + capability + tenant scope |
| Operator | Understand payment status | Sanitized status, no provider secrets |
| Platform admin | Diagnose failures | Sanitized health and logs only |
| Automation/n8n | Receive settlement/payment events | HMAC, idempotency and allowlisted payload |

## 6. Functional requirements

### RF-MP-1 — OAuth and connection feedback

The UI must show accurate success/error feedback after Mercado Pago OAuth callback regardless of provider slug shape in the query string.

### RF-MP-2 — Token refresh lifecycle

Provider operations must request a valid access token from a backend credential manager. Expired tokens refresh atomically; invalid/revoked refresh tokens put the connection in reauth-required/degraded state.

### RF-MP-3 — Webhook intake

Mercado Pago webhooks must be validated, persisted idempotently, processed asynchronously and safely mapped to tenant/provider resources.

### RF-MP-4 — Payment status sync

Webhook/fetch processing must update internal `Payment` status idempotently, without terminal-state regressions, and with audit/notifications for meaningful transitions.

### RF-MP-5 — Cancel/refund

Authorized users can cancel/refund Mercado Pago payments only when internal state and provider policy allow it. Invalid operations return translated user-friendly errors.

### RF-MP-6 — Financial readiness

LedgerFlow can determine whether a Mercado Pago connection is payment-only or settlement-readable based on scopes, token health and financial-read capability.

### RF-9B-1 — Financial accounts

Authorized users can create operational financial accounts and opening balances. Cash ledger movements are append-only and audited.

### RF-9B-2 — Financial ingestion

Mercado Pago financial data can be fetched by period, normalized, sanitized and upserted as idempotent settlement events.

### RF-9B-3 — ML x MP matching

Settlement matching prioritizes exact provider identifiers. Amount/date matches are candidates only and require manual review.

## 7. UX and design system

- Preserve the current dark enterprise visual language, layout rhythm and design tokens.
- Reuse existing components such as page headers, cards, tables, modals, badges, empty/error states, buttons and toasts.
- Use localized messages and status labels from `pt-BR` and `en-US`.
- Make reauth/degraded states explicit without exposing technical secrets.
- Long-running syncs must show immediate feedback and prevent duplicate submissions.
- Financial dashboards must include the disclaimer: operational management view; not official accounting.

## 8. Success metrics

- Zero token/secret exposure in UI, logs, audit, queues or notifications.
- Zero webhook cross-tenant attachment.
- Duplicate webhooks do not duplicate status transitions, audit or notifications.
- Expired tokens refresh without user reconnection during normal operation.
- Mercado Pago PIX E2E path has documented evidence before 9B ingestion starts.
- Settlement events are idempotent and searchable by provider identifiers.
