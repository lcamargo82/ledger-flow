# SDD — 10.2 Notification Center & Advanced Inventory

**Status:** 10.2.0A e 10.2.0B implementadas; estoque 10.2.1–10.2.3 planejado. Contratos futuros não aparecem no OpenAPI/AsyncAPI antes da sprint correspondente.

## 1. Fronteiras

```text
notifications → eventos internos, recipients, leitura, outbound delivery
inventory     → transferências, contagens, ledger e saldos
auth/platform → tenant, usuário, RBAC, capabilities e audit
async         → Outbox, RabbitMQ, retry, DLQ e replay
web           → apresentação; nunca decide autorização final
```

Notifications consome eventos normalizados; não importa adapters de Mercado Livre, Asaas ou regras de estoque. Inventory publica fatos e não conhece componentes Vue ou Telegram.

## 2. Decisões técnicas

- Manter REST/NestJS/Prisma/PostgreSQL e envelopes de paginação existentes.
- Usar UUID, `DateTime`/TIMESTAMPTZ e relações normalizadas.
- Usar JSON apenas para argumentos de tradução e metadata allowlisted; ownership, estado e índices ficam em colunas.
- Usar polling inicial em `unread-count`; WebSocket é evolução posterior baseada em medição.
- Reutilizar `InventoryMovement` e `InventoryBalance`; não criar saldo paralelo.

## 3. Modelo de notificações

### NotificationEvent

```text
id UUID PK
tenantId FK Tenant
category NotificationCategory
eventType String
severity NotificationSeverity
titleKey String
messageKey String
translationArgsJson Json?
metadataJson Json?
sourceType String
sourceId String?
idempotencyKey String
requiredPermissions String[]
requiredCapabilities String[]
occurredAt DateTime
createdAt DateTime
```

Índices:

```text
UNIQUE (tenantId, idempotencyKey)
INDEX  (tenantId, category, createdAt DESC)
INDEX  (tenantId, sourceType, sourceId)
```

### NotificationRecipient

```text
id UUID PK
tenantId FK Tenant
notificationEventId FK NotificationEvent
userId FK User
readAt DateTime?
dismissedAt DateTime?
deliveredAt DateTime?
createdAt DateTime
updatedAt DateTime
```

Índices:

```text
UNIQUE (notificationEventId, userId)
INDEX  (tenantId, userId, readAt, createdAt DESC)
INDEX  (tenantId, userId, dismissedAt, createdAt DESC)
```

### Outbound notification webhook

`NotificationWebhookSubscription` guarda endpoint, status, event filter e segredo cifrado pelo serviço central. `NotificationWebhookDelivery` guarda tentativa, status, próxima tentativa, response code sanitizado e idempotency key. Nunca guardar header Authorization ou corpo remoto bruto.

## 4. Pipeline de notificação

```text
evento normalizado/outbox
→ NotificationService.createEvent()
→ unique tenantId + idempotencyKey
→ NotificationAudienceResolver
→ users ativos do tenant + RBAC + capabilities
→ recipients em transação
→ notification.created
→ UI polling / outbound dispatcher
```

### Autorização em duas camadas

1. **Delivery-time:** não criar recipient para usuário inelegível.
2. **Read-time:** aplicar tenant, userId e política atual da categoria; revogação de acesso passa a ocultar conteúdo já entregue.

Mapeamentos de categoria/evento ficam em registry backend versionado, não em parâmetros livres enviados pelo frontend.

## 5. APIs de notificações

```text
GET   /notifications?cursor=&limit=&category=&unread=&severity=&from=&to=
GET   /notifications/unread-count
PATCH /notifications/:id/read
POST  /notifications/read-all
DELETE /notifications/:id
```

- Cursor por `(createdAt,id)` evita inconsistência em feed mutável.
- `PATCH .../read` é idempotente e retorna o recipient atualizado.
- `DELETE` representa dismiss lógico e retorna 204.
- Erros seguem o formato Nest existente, com códigos estáveis documentados nos DTOs/Swagger.

Administração futura de outbound:

```text
GET    /notification-webhook-subscriptions
POST   /notification-webhook-subscriptions
PATCH  /notification-webhook-subscriptions/:id
DELETE /notification-webhook-subscriptions/:id
POST   /notification-webhook-subscriptions/:id/test
POST   /notification-webhook-subscriptions/:id/rotate-secret
GET    /notification-webhook-subscriptions/:id/deliveries
POST   /notification-webhook-subscriptions/:id/deliveries/:deliveryId/replay
```

Assinatura: `X-LedgerFlow-Timestamp`, `X-LedgerFlow-Signature: v1=<HMAC_SHA256>` sobre `timestamp + '.' + rawBody`; janela antireplay documentada. Delivery usa Outbox/worker, backoff+jitter, limite de tentativas e DLQ.
O segredo cifrado nunca é retornado; o texto puro aparece somente nas respostas de criação e rotação. A criação do `NotificationEvent`, da `NotificationWebhookDelivery` e do evento `notification.webhook.delivery_requested` no Outbox ocorre na mesma transação.
Teste e replay retornam `202`; replay aceita somente delivery `DLQ`, reivindica a transição atomicamente e registra `AuditLog`. A consulta operacional retorna contagens por status e deliveries recentes sem idempotency key, payload ou corpo externo.

## 6. Advanced Inventory

### InventoryTransfer

```text
id, tenantId, transferNumber
sourceWarehouseId, destinationWarehouseId
status, reasonCode, notes
idempotencyKey
createdByUserId, completedByUserId?, canceledByUserId?
createdAt, updatedAt, completedAt?, canceledAt?
```

### InventoryTransferItem

```text
id, tenantId, transferId, skuId
quantity Decimal(18,6)
unitCostSnapshot Decimal(18,4)?
createdAt
```

Restrições/índices:

```text
UNIQUE (tenantId, transferNumber)
UNIQUE (tenantId, idempotencyKey)
UNIQUE (transferId, skuId)
INDEX  (tenantId, status, createdAt DESC)
CHECK  sourceWarehouseId <> destinationWarehouseId
CHECK  quantity > 0
```

Conclusão executa uma única transação:

```text
lock/recheck balances
→ validar available na origem
→ InventoryMovement TRANSFER_OUT idempotency transfer:<id>:<item>:out
→ InventoryMovement TRANSFER_IN  idempotency transfer:<id>:<item>:in
→ atualizar balances/version
→ status COMPLETED
→ AuditLog + Outbox
```

### CycleCount

```text
id, tenantId, countNumber, warehouseId
status, reasonCode?, notes?
idempotencyKey
createdByUserId, openedByUserId?, approvedByUserId?
openedAt?, countedAt?, approvedAt?, adjustedAt?, canceledAt?
createdAt, updatedAt
```

### CycleCountItem

```text
id, tenantId, cycleCountId, skuId
systemOnHandAtOpen Decimal(18,6)
balanceVersionAtOpen Int
countedQuantity Decimal(18,6)?
varianceQuantity Decimal(18,6)?
countedByUserId?, countedAt?
adjustmentMovementId?
```

Restrições/índices:

```text
UNIQUE (tenantId, countNumber)
UNIQUE (tenantId, idempotencyKey)
UNIQUE (cycleCountId, skuId)
INDEX  (tenantId, warehouseId, status, createdAt DESC)
CHECK  countedQuantity >= 0
```

Na aprovação, se `InventoryBalance.version != balanceVersionAtOpen`, retornar 409 `CYCLE_COUNT_STALE_BALANCE`; nenhum ajuste parcial. Após validação, gerar `ADJUSTMENT_IN/OUT` por item divergente, atualizar balances, auditar e publicar `inventory.balance.changed` na mesma estratégia já usada pelo Inventory.

## 8. Permissões e capabilities

```text
notifications:read          + notifications.read
notifications:manage        + notifications.manage
inventory:read              + inventory.manage (compatibilidade)
inventory:transfer          + inventory.transfer
inventory:cycle-count       + inventory.cycle_count
inventory:approve           + inventory.approval
inventory:alerts-manage     + inventory.alerts.manage
inventory:aging-read        + inventory.aging.read
inventory:kits-manage       + inventory.kits.manage
```

Permissões novas entram em seed/migration idempotente e matriz de roles; capabilities entram no registry e entitlements. Rotas não devem exigir `inventory.manage` indiscriminadamente quando uma capability mais estreita existir.

## 9. UI

- `NotificationBell` no footer antes do usuário, com target mínimo 44×44 e badge `99+`.
- `/notifications`: `AppPageHeader`, filtros com disclosure progressivo, lista, empty/loading/error e paginação/cursor.
- `/inventory/transfers` e `/inventory/cycle-counts`: tabelas com ações por estado; formulários em modal somente quando curtos, detalhes em página quando houver múltiplos itens.
- Destructive/irreversible actions usam `AppConfirmDialog`; aprovação mostra resumo da consequência.
- Status sempre usa `AppBadge`/mapeamento semântico e texto localizado, nunca apenas cor.

## 10. Migração e rollout

1. Criar enums/tabelas nullable quando necessário e índices.
2. Gerar Prisma Client e validar migration em cópia de dados.
3. Deploy backend sem produtores; depois UI; depois habilitar produtores por feature flag/capability.
4. Backfill não é necessário para notificações antigas.
5. Outbound subscriptions começam desativadas.
6. Rollback desabilita producers/rotas antes de remover schema; nenhuma migration destrutiva na mesma release.

## 11. Observabilidade e segurança

Métricas: eventos criados/duplicados, recipients, unread latency, delivery retry/DLQ, transfer completion/failure, stale cycle count e adjustment totals. Logs usam IDs, códigos e traceId; não usam título traduzido, metadata completa, HMAC secret ou payload externo bruto.

## 12. Documentação executável

- Decorators Nest geram Swagger `/api/docs`, Redoc `/api/reference` e `/api/openapi.json`.
- Cada endpoint inclui DTO, exemplos, permission/capability e respostas de erro.
- AsyncAPI recebe `notification.created`, `notification.webhook.delivery_requested`, `inventory.transfer.completed`, `inventory.cycle_count.adjusted` somente quando registrados no publisher/consumer.
