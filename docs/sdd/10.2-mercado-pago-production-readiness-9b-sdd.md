# SDD — 10.2 Mercado Pago Production Readiness & 9B Preparation

**Status:** planned.
**Aggregate branch:** `feature/10.2`.

## 1. Boundaries

```text
gateways/mercado-pago
  OAuth, credentials, payment operations and provider client

webhooks
  Mercado Pago inbound validation, inbox persistence and async trigger

payments
  internal payment status transitions, audit and payment events

notifications
  authorized internal notifications and sanitized outbound n8n delivery

settlement/9B
  financial accounts, Mercado Pago financial facts, matching and cash views

web
  presentation only; never authorization source of truth
```

Payment gateway operations and financial settlement reads may share a connection, but application services must stay separate.

## 2. Configuration model

Global `.env` may contain only app-level configuration:

```text
MERCADO_PAGO_CLIENT_ID
MERCADO_PAGO_CLIENT_SECRET
MERCADO_PAGO_BASE_URL
```

```text

```

Never put tenant access/refresh tokens in `.env`.

## 4. Token refresh lifecycle

Introduce `MercadoPagoCredentialManager` or equivalent.

Responsibilities:

- Load encrypted credentials by tenant/configuration.
- Decrypt credentials only in memory.
- Refresh when `tokenExpiresAt <= now + threshold`.
- Use distributed lock key `lock:mercado-pago:refresh:{gatewayConfigurationId}`.
- Persist rotated tokens atomically.
- Preserve merchant id/scopes.
- Increment version or use optimistic guard when available.
- Mark reauth-required/degraded on unrecoverable auth errors.
- Return a valid access token to provider operations.

Provider methods must not read stale encrypted credentials directly when an operation requires an access token.

MP-1 implementation: `MercadoPagoCredentialManager` is the credential boundary for Mercado Pago payment operations. It uses Redis `SET NX EX` locking, optimistic encrypted-credential matching on update, sanitized audit actions, and Notification Center event `mercado_pago.connection_reauth_required` for unrecoverable refresh failures.

## 5. Webhook architecture

Endpoint:

```text
POST /webhooks/mercado-pago
```

The webhook URL must not point to OAuth callback.

Flow:

```text
Mercado Pago
→ signature validation
→ WebhookInboxEvent
→ OutboxEvent webhook.inbound_processing_requested
→ quick HTTP response
→ provider-aware worker
→ fetches Mercado Pago payment details when needed
→ updates Payment status when the transition is safe
→ creates sanitized PaymentEvent/AuditLog
→ emits authorized NotificationEvent when status changes
```

Signature policy:

- Configured secret + valid signature: process.
- Configured secret + invalid signature: reject in production.
- Missing secret in production: reject.
- Missing secret outside production: allow only with warning and explicit signature status.

Tenant resolution order:

1. Merchant/account id mapped to active `GatewayConfiguration`.
2. Existing `Payment.providerPaymentId`.
3. Existing external reference.
4. Known tenant-scoped mapping.

Never trust provider payload alone to choose tenant.

MP-2 implementation: `MercadoPagoWebhooksController`, `MercadoPagoWebhookAuthenticator`, `MercadoPagoWebhookNormalizer` and `MercadoPagoWebhookProcessor` implement the intake foundation. The inbox stores only sanitized summaries and queues the existing generic `webhook.inbound_processing_requested` command; `mercado_pago.webhook_received` is not emitted yet because no provider-specific consumer exists. Merchant id can attach to a tenant only through the stored `GatewayConfiguration.credentialsFingerprint = mp_{merchantId}` mapping. The generic worker skips Asaas settlement ingestion for non-Asaas providers.

MP-3 implementation: `PaymentWebhookSyncService.syncMercadoPagoPayment` resolves the local payment through provider id or external reference, obtains a valid Mercado Pago token through `MercadoPagoCredentialManager`, fetches the provider payment via `MercadoPagoPaymentGatewayAdapter`, applies `MercadoPagoStatusMapper`, and writes sanitized `PaymentEvent`/`AuditLog` records only for meaningful transitions. `APPROVED` does not regress to pending/failed; `REFUNDED` and `CANCELED` are terminal; chargeback-like statuses create `payment.provider_chargeback_received` without changing local payment status.

## 6. Payment status policy

Initial mapping:

| Mercado Pago status      | LedgerFlow status                                          |
| ------------------------ | ---------------------------------------------------------- |
| `approved`, `accredited` | `APPROVED`                                                 |
| `pending`, `in_process`  | `PENDING` or existing `PROCESSING` policy                  |
| `rejected`               | `FAILED`                                                   |
| `cancelled`              | `CANCELED` if supported, otherwise existing failure policy |
| `refunded`               | `REFUNDED`                                                 |
| chargeback/contest       | domain event/case if enum cannot represent it accurately   |

Rules:

- Status transitions are idempotent.
- Terminal statuses do not regress without explicit policy.
- Provider status detail is stored sanitized.
- Audit and notifications are created only for meaningful transitions.
- Mercado Pago chargeback-like statuses are represented as events/cases, not inaccurate local payment status changes.

## 7. Cancel/refund architecture

Use existing `IPaymentGateway` methods:

```text
cancelPayment
refundPayment
```

Application layer must enforce:

- Permission.
- Tenant ownership.
- Allowed current state.
- Reason requirement.
- Idempotency key.
- Sanitized audit and notification.

Provider response must be mapped to a neutral operation result; raw provider payload must not leak to UI/logs.

MP-4 implementation: `MercadoPagoPaymentGatewayAdapter.cancelPayment` updates the provider payment status to cancelled through the Mercado Pago API, and `refundPayment` creates a full refund through the provider refunds endpoint. `GatewayPaymentOrchestrationService` resolves fresh Mercado Pago credentials before both operations and sends deterministic idempotency keys. `PaymentsService` calls the provider before local mutation, stores sanitized provider status/refund identifiers in `PaymentEvent`/`AuditLog` metadata, requires a refund reason, and treats already canceled/refunded local state as an idempotent success.

MP-4 capability matrix: Mercado Pago currently advertises PIX, boleto, sandbox, inbound webhook foundation, webhook/fetch payment status sync, cancel and full refund. Partial refund, card, bank transfer, checkout redirect and embedded checkout remain unsupported until their implementation sprints land.

## 7.1. Production payment E2E validation

MP-5 does not add a new runtime boundary. It formalizes the operational evidence path in `docs/runbooks/mercado-pago-payment-e2e.md` and ties existing implementation points into one repeatable validation:

```text
OAuth connection
→ GatewayConfiguration ACTIVE
→ PIX or boleto Payment created through PaymentsController
→ Mercado Pago webhook signature authenticated
→ WebhookInboxEvent persisted idempotently
→ PaymentWebhookSyncService fetches provider status with fresh credentials
→ PaymentEvent/AuditLog recorded with sanitized metadata
→ NotificationProducerService creates authorized internal notification
→ outbound webhook delivery signs normalized event for n8n
```

The runbook is intentionally evidence-driven: repository tests verify signature, refresh, dedupe planning and status-sync behavior, while real PIX/boleto execution must be captured in staging/production without storing provider tokens, secrets or raw provider payloads.

## 8. 9B settlement readiness

Short-term decision: reuse `GatewayConfiguration` for Mercado Pago settlement-read readiness.

Do not put financial ingestion inside the payment adapter. Add separate services such as:

```text
MercadoPagoFinancialReadService
MarketplaceSettlementIngestionService
MarketplaceSettlementMatchingService
```

Financial readiness checks:

- Merchant id present.
- Required read/offline scopes present.
- Token health is active.
- Financial-read capability is enabled.
- Last sync success/failure timestamps are visible.

MP-6 implementation: readiness is a derived response field instead of a new persistence model. `GatewayConnectionResponseDto.financialReadiness` uses `GatewayConfiguration.status`, `healthStatus`, `lastHealthCheckAt`, `lastHealthCheckMessage` and decrypted Mercado Pago `scope` values to return one of `NOT_CONFIGURED`, `REAUTH_REQUIRED`, `UNHEALTHY`, `PAYMENT_ONLY` or `SETTLEMENT_READY`. The required settlement-read scopes are `offline_access` and `read`.

`MercadoPagoFinancialReadinessService` is the boundary future 9B ingestion services must call before Mercado Pago financial I/O. Its `assertSettlementReadable` method blocks reauth, unhealthy and payment-only connections. Payment gateway adapters remain payment-only and do not import settlement responsibilities.

Short-term persistence decision: continue using `GatewayConfiguration` for readiness because MP-6 only needs status, health and encrypted scopes. Revisit a dedicated `FinancialIntegrationConnection` when any of these become necessary: provider-specific last financial sync cursor, per-financial-account credentials, multiple settlement accounts per provider, independent financial health state or sync scheduling that should survive payment connection status changes.

9B-1 implementation: settlement cash starts with tenant-scoped `OperationalFinancialAccount` records linked to a settlement-ready Mercado Pago `GatewayConfiguration`. Account creation is guarded by `marketplace-settlement:manage` plus `marketplace_settlement.manage`, calls `MercadoPagoFinancialReadinessService.assertSettlementReadable`, and stores opening balance in minor units. Every opening balance creates an append-only `CashLedgerEntry` with type `OPENING_BALANCE`, a `CashPositionAdjustment` with type `OPENING_BALANCE`, initializes `currentBalanceMinor`, and writes sanitized `AuditLog` metadata. Manual corrections use `CashLedgerEntryType.MANUAL_ADJUSTMENT` and `CashPositionAdjustmentType.MANUAL_CORRECTION`; they append new entries and update the account balance, never rewriting prior ledger rows.

9B-1 UI: `/marketplace-settlement` is available to users with `marketplace-settlement:read` and `marketplace_settlement.read`. It lists Mercado Pago operational accounts, current/opening balance and the append-only ledger. The create flow only offers Mercado Pago connections whose `financialReadiness.canReadSettlements` is true. All labels and errors live under `marketplaceSettlement.*` in pt-BR/en-US.

9B-2 implementation: Mercado Pago financial ingestion stays outside the payment adapter. `MercadoPagoFinancialReadService` calls provider payment search using credentials resolved by `MercadoPagoCredentialManager` with `purpose: SETTLEMENT`, then normalizes each payment into a sanitized `NormalizedSettlementEvent`. The existing 9A `ProviderSettlementEvent` table is reused and extended with nullable `operationalFinancialAccountId`, allowing settlement events to remain searchable by provider identifiers while also being scoped to the selected marketplace cash account. Manual sync runs through `MarketplaceFinancialIngestionService`, validates `MercadoPagoFinancialReadinessService.assertSettlementReadable`, imports through `ReconciliationSettlementIngestionService` to preserve idempotency, and emits `marketplace_settlement.event_received` outbox messages for new rows. Stored normalized payloads contain only operational fields such as provider payment id, status, gross/fee/net minor-unit amounts, release date, fee types and sanitized refund summaries; raw provider payloads, QR payloads, tokens and secrets are excluded.

9B-2 UI/API: `POST /marketplace-settlement/financial-accounts/:id/sync` performs manual period sync, `GET /marketplace-settlement/financial-accounts/:id/events` lists imported facts, and `GET /marketplace-settlement/financial-accounts/:id/totals` returns initial gross/fee/net totals. The `/marketplace-settlement` screen exposes sync controls, sync summary, imported totals and imported events using the existing dark enterprise layout and pt-BR/en-US translation keys.

9B-3 implementation: matching now bridges Mercado Pago settlement facts and Mercado Livre operational order facts without crossing tenant boundaries. `OrderFinancialFact.externalOrderId` stores the marketplace order identifier in a structured indexed column, while `ReconciliationCase.orderId` references `InternalOrder` so cases can carry payment and/or order evidence. `ReconciliationMatchingService` preserves the existing precedence: provider payment id, payment external/reference, then exact Mercado Livre external order id. Exact order-id matches compare settlement amount/currency against order revenue in minor units and can reconcile only when aligned; otherwise they produce explicit amount/currency divergence cases. Amount/date matches against payments or Mercado Livre order facts are candidate-only and become `PENDING` cases for manual review, never final automatic reconciliation.

9B-4 implementation: cash position and P&L remain derived views and add no new persistence. `MarketplaceFinancialIngestionService.getDashboard` reads the selected tenant/account, imported `ProviderSettlementEvent` rows and matched `ReconciliationCase.orderId` values. Cash buckets are calculated in minor units: released uses net event amounts whose `availableAt` is due, pending uses approved future/undated amounts, blocked uses pending/in-process/mediation/chargeback provider states, refunded uses refund/refunded events, and payout remains zero until payout events exist. Operational P&L uses matched latest `OrderFinancialFact` rows for revenue, COGS and freight, and imported settlement events for fees/refunds. The API and UI carry the disclaimer: operational management view only, not official accounting.

9B-5 implementation: fine mesh reuses 9A `ReconciliationCase` and `ReconciliationDecision` instead of creating a parallel settlement case model. `RECONCILIATION_REASON_CODES` is the backend registry for action-specific decisions and exposes label keys to the web app through `GET /reconciliation/cases/reason-codes`. `ReconciliationDecisionsService` validates the reason/action pair and required comments before writing immutable decisions and audit logs. `ReconciliationCasesService.getTimeline` returns sanitized evidence from `ProviderSettlementEvent`, linked `Payment`, linked `InternalOrder`, immutable decisions and ordered timeline events. The web review modal renders evidence/timeline with existing design tokens and pt-BR/en-US translations before the user records resolve/ignore/reopen/comment/manual-match decisions.

9B-6 implementation: settlement alerts reuse the existing Notification Center and outbound webhook delivery tables. `notification-event-registry` now registers `marketplace_settlement.event_received` and `cash_position.unexplained_difference` with reconciliation and marketplace-settlement permission/capability requirements. `NotificationProducerService.marketplaceSettlementEventReceived` creates idempotent, sanitized `NotificationEvent` rows from new `ProviderSettlementEvent` records; `NotificationWebhookDeliveryPlannerService` schedules outbound deliveries for active subscriptions whose `eventTypes` include the settlement event. The executor continues to sign `timestamp.rawBody` with HMAC, send `Idempotency-Key`, retry transient failures and avoid raw provider payloads/secrets in delivery bodies.
