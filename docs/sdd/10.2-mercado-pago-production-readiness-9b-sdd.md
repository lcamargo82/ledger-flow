# SDD — 10.2 Mercado Pago Production Readiness & 9B Preparation

**Status:** planned.
**Aggregate branch:** `feature/10.2`.

## 1. Boundaries

```text
gateways/mercado-pago
  OAuth, credentials, payment operations and provider client

webhooks
  Mercado Pago inbound validation, inbox persistence and async trigger

payments
  internal payment status transitions, audit and payment events

notifications
  authorized internal notifications and sanitized outbound n8n delivery

settlement/9B
  financial accounts, Mercado Pago financial facts, matching and cash views

web
  presentation only; never authorization source of truth
```

Payment gateway operations and financial settlement reads may share a connection, but application services must stay separate.

## 2. Configuration model

Global `.env` may contain only app-level configuration:

```text
MERCADO_PAGO_CLIENT_ID
MERCADO_PAGO_CLIENT_SECRET
MERCADO_PAGO_BASE_URL
MERCADO_PAGO_OAUTH_BASE_URL
MERCADO_PAGO_OAUTH_REDIRECT_URI
MERCADO_PAGO_TEST_MODE
```

Tenant-scoped credentials remain encrypted in `GatewayConfiguration.encryptedCredentials`:

```text
accessToken
refreshToken
tokenExpiresAt
merchantId
scope/grantedScopes
credentialsVersion if added
```

Never put tenant access/refresh tokens in `.env`.

## 3. Provider slug policy

Canonical internal provider:

```text
MERCADO_PAGO
```

Canonical URL/query slug:

```text
mercado-pago
```

Frontend must normalize accepted legacy values:

```text
mercado-pago
mercado_pago
MERCADO_PAGO
```

All comparisons should go through a helper/mapping, not raw string checks in views.

MP-0 implementation: `apps/web/src/utils/gateway-provider.ts` normalizes the accepted aliases above and keeps unknown values closed.

## 4. Token refresh lifecycle

Introduce `MercadoPagoCredentialManager` or equivalent.

Responsibilities:

- Load encrypted credentials by tenant/configuration.
- Decrypt credentials only in memory.
- Refresh when `tokenExpiresAt <= now + threshold`.
- Use distributed lock key `lock:mercado-pago:refresh:{gatewayConfigurationId}`.
- Persist rotated tokens atomically.
- Preserve merchant id/scopes.
- Increment version or use optimistic guard when available.
- Mark reauth-required/degraded on unrecoverable auth errors.
- Return a valid access token to provider operations.

Provider methods must not read stale encrypted credentials directly when an operation requires an access token.

## 5. Webhook architecture

Endpoint:

```text
POST /webhooks/mercado-pago
```

The webhook URL must not point to OAuth callback.

Flow:

```text
Mercado Pago
→ signature validation
→ WebhookInboxEvent
→ OutboxEvent mercado_pago.webhook_received
→ quick HTTP response
→ worker resolves tenant/resource
→ fetches provider resource when needed
→ normalizes event
→ updates Payment or creates settlement candidate
→ publishes notifications/outbound events when applicable
```

Signature policy:

- Configured secret + valid signature: process.
- Configured secret + invalid signature: reject in production.
- Missing secret in production: reject.
- Missing secret outside production: allow only with warning and explicit signature status.

Tenant resolution order:

1. Merchant/account id mapped to active `GatewayConfiguration`.
2. Existing `Payment.providerPaymentId`.
3. Existing external reference.
4. Known tenant-scoped mapping.

Never trust provider payload alone to choose tenant.

## 6. Payment status policy

Initial mapping:

| Mercado Pago status | LedgerFlow status |
|---|---|
| `approved`, `accredited` | `APPROVED` |
| `pending`, `in_process` | `PENDING` or existing `PROCESSING` policy |
| `rejected` | `FAILED` |
| `cancelled` | `CANCELED` if supported, otherwise existing failure policy |
| `refunded` | `REFUNDED` |
| chargeback/contest | domain event/case if enum cannot represent it accurately |

Rules:

- Status transitions are idempotent.
- Terminal statuses do not regress without explicit policy.
- Provider status detail is stored sanitized.
- Audit and notifications are created only for meaningful transitions.

## 7. Cancel/refund architecture

Use existing `IPaymentGateway` methods:

```text
cancelPayment
refundPayment
```

Application layer must enforce:

- Permission.
- Tenant ownership.
- Allowed current state.
- Reason requirement.
- Idempotency key.
- Sanitized audit and notification.

Provider response must be mapped to a neutral operation result; raw provider payload must not leak to UI/logs.

MP-0 capability matrix: Mercado Pago currently advertises PIX, boleto and sandbox only. Cancel, refund, partial refund, card, bank transfer, checkout redirect, embedded checkout and webhooks remain unsupported until their implementation sprints land.

## 8. 9B settlement readiness

Short-term decision: reuse `GatewayConfiguration` for Mercado Pago settlement-read readiness.

Do not put financial ingestion inside the payment adapter. Add separate services such as:

```text
MercadoPagoFinancialReadService
MarketplaceSettlementIngestionService
MarketplaceSettlementMatchingService
```

Financial readiness checks:

- Merchant id present.
- Required read/offline scopes present.
- Token health is active.
- Financial-read capability is enabled.
- Last sync success/failure timestamps are visible.

## 9. 9B domain candidates
