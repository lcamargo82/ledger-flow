# SDD — 11.0 Sales Intelligence Core

## Boundary

Sales Intelligence is a read layer. Orders own orders, Inventory owns reservations/movements, Financial Intelligence owns operational facts, and 9B owns settlement events/cases.

## API

```text
GET /sales-intelligence
GET /sales-intelligence/summary
```

Both endpoints require `sales-intelligence:read` and `sales_intelligence.read`. The backend derives `tenantId` from the authenticated user.
List and summary accept the same period, order reference, payment status and stock status filters. List pagination is executed in PostgreSQL with a maximum page size of 100; summary processing uses stable cursor batches of 500 records.

## Money and provenance

Money leaves the API as strings in minor units. `netAmountSource` is mandatory whenever a net value is returned:

```text
REALIZED    → confirmed/released Mercado Pago value ingested by 9B
RECONCILED  → settlement value linked to the order by reconciliation
ESTIMATED   → operational order value less known fees
UNAVAILABLE → source data is insufficient; never coerce to zero
```

## Query strategy

The read model paginates from `InternalOrder`, selects only the current Mercado Livre operational fact, loads item/reservation state and resolves linked Mercado Pago reconciliation cases without N+1 queries. Financial changes create immutable revisions; an SHA-256 signature makes an unchanged replay idempotent, while `isCurrent` identifies the authoritative revision. Revision replacement runs in a serializable transaction and the database enforces one current fact per order.

The 11.0.4 validation confirmed the supporting indexes on `(tenantId, createdAt)`, current Mercado Livre facts by sold date/payment status, and tenant/order relations. Summary traversal now uses the `InternalOrder.id` cursor rather than increasingly expensive offsets. The bounded 501-order regression test did not justify a parallel materialized snapshot.

Stock filtering is derived from `InventoryReservation`: missing, active, consumed and released reservations map to `PENDING`, `RESERVED`, `CONSUMED` and `RELEASED`; mixed item states map to `DIVERGENT`. No parallel stock ledger is created.

## Frontend

`SalesIntelligenceView.vue` reuses the common page, table, drawer, badge and state components. `AppMetricGrid` and `AppMetricCard` now keep the Sales Intelligence and Analytics indicators on the same compact, responsive visual pattern. The final Core uses LedgerFlow tokens and pt-BR/en-US translations without mocked financial or profitability data.

## Security

- RBAC and capability checks are enforced by backend guards.
- No raw provider payload, secret, buyer-sensitive detail or token is returned.
- Provider IDs remain strings.
- Money is persisted as decimal operational data and serialized as strings in minor units.
- Logs and OpenAPI examples stay sanitized.
- Runtime dependencies were upgraded within Nest 11 to Multer 2.2.0 and js-yaml 4.3.0; the production dependency audit closes with zero findings.
