# Runbook — 10.2 Operational Readiness

**Status:** 10.2.0A–10.2.3 implementadas.

## Configuração 10.2.0A

- `NOTIFICATIONS_INTERNAL_PRODUCERS_ENABLED=false`: rollout seguro dos produtores de falha de canal e divergência de conciliação.
- `VITE_NOTIFICATIONS_POLLING_INTERVAL_MS=30000`: polling do contador; valores abaixo de 10000 são elevados para 10 segundos.
- Habilitar produtores somente após migration, seed de permissões e smoke test de feed/count.

## Configuração 10.2.0B

- `NOTIFICATION_WEBHOOK_TIMEOUT_MS=10000`: timeout por tentativa HTTP.
- `NOTIFICATION_WEBHOOK_RETRY_BASE_MS=30000`: base do backoff exponencial.
- `NOTIFICATION_WEBHOOK_RETRY_MAX_MS=1800000`: teto do backoff antes da próxima tentativa.
- O worker consome `ledgerflow.notifications.webhooks.q`; respostas 408, 425, 429, 5xx, timeout e falha de rede reagendam pelo Outbox com jitter.
- Respostas 4xx permanentes, endpoint inseguro, segredo inválido ou esgotamento de tentativas movem a delivery para `DLQ` sem logar segredo ou corpo externo.
- O consumidor deve deduplicar pelo header `Idempotency-Key` e validar `X-LedgerFlow-Timestamp` e `X-LedgerFlow-Signature` sobre `timestamp.rawBody`.
- Vetor de validação e exemplo seguro: `docs/reference/notification-webhook-consumer.md`.
- Triagem de segurança da fase: `docs/reference/10.2.0b-security-assessment.md`.

## Go/No-Go

| Área         | Critério                                                      |
| ------------ | ------------------------------------------------------------- |
| Tenant       | nenhum read/write cross-tenant em notification/transfer/count |
| RBAC         | recipient e leitura respeitam permissão/capability atual      |
| Idempotência | replay não duplica evento, recipient, movimento ou ajuste     |
| Transfer     | falha em um item faz rollback integral                        |
| Cycle count  | saldo versionado mudou → 409, sem ajuste                      |
| Async        | worker aplica retry/DLQ e replay sanitizado                   |
| Webhook      | HMAC/antireplay e rotação de segredo validados                |
| UI           | estados, foco, contraste, responsive e pt-BR/en-US            |
| Docs         | Swagger/Redoc/AsyncAPI/README/UI docs coerentes com código    |

## Smoke tests

1. Criar notificação duplicada e confirmar um único evento/recipient.
2. Revogar permissão e confirmar que feed/count deixam de revelar o item.
3. Indisponibilizar n8n, observar retry/DLQ e reprocessar sem duplicar mensagem.
4. Executar `POST .../:id/test`, consultar `GET .../:id/deliveries` e confirmar a transição até `DELIVERED`.
5. Reprocessar uma DLQ e confirmar um único AuditLog `notifications.webhook.delivery_replayed`.
6. Concluir transferência multi-item e validar pares OUT/IN e balances.
7. Forçar falha no segundo item e confirmar rollback total.
8. Abrir contagem, movimentar SKU e confirmar bloqueio stale.
9. Reabrir/recontar, aprovar e validar ajuste/audit/notification.
