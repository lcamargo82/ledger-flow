# Spec — 10.2 Mercado Pago Production Readiness & 9B Preparation

**Status:** planned after 10.2.3 and after merging `feature/10.1-11-ml-enrichment` into `feature/10.2`.
**Source spec:** `/Users/leandro/Downloads/ledgerflow_mercado_pago_production_readiness_9b_spec.md`.
**Branch model:** use `feature/10.2` as the aggregate branch; create one child branch per sprint and merge it back into `feature/10.2`.

## Goal

Make Mercado Pago production-ready as a payment gateway first, then prepare reliable financial data for the 9B Marketplace Settlement program.

The safe order is:

```text
Mercado Pago payment readiness
→ webhook/status reliability
→ production E2E evidence
→ financial readiness
→ 9B settlement foundation
```

Do not start full 9B settlement matching from assumptions. It must consume sanitized, tenant-safe, idempotent Mercado Pago facts.

## Current baseline

Implemented today:

- `PaymentProvider.MERCADO_PAGO` and `WebhookProvider.MERCADO_PAGO`.
- OAuth connect/callback/disconnect/status endpoints.
- Encrypted tenant credentials in `GatewayConfiguration`.
- Mercado Pago API client for token exchange, refresh, create payment and fetch payment.
- Payment adapter for PIX/boleto create, fetch and instructions.
- Generic async charge handler resolves Mercado Pago through `PaymentGatewayFactoryService`.
- Initial frontend connection UI and service.

Partial or missing:

- Automatic refresh lifecycle is not fully wired into provider operations.
- Webhook adapter exists but throws `WebhookProviderNotSupportedError`.
- Cancel/refund operations are not implemented.
- Card support must not be advertised as production-ready.
- OAuth callback provider slug is inconsistent between backend and frontend.
- Settlement/reconciliation is not implemented.

## Cross-cutting rules for every sprint

- Keep tenant access tokens and refresh tokens only in encrypted database credentials; never in `.env`, API responses, logs, audit metadata, queues or frontend state.
- `.env` only stores application-level Mercado Pago app configuration such as client id, client secret, base URLs and redirect URI.
- OAuth callback URL and webhook URL are different:
  - OAuth: `/gateways/mercado-pago/oauth/callback` or the eventual canonical integration callback.
  - Webhook: `/webhooks/mercado-pago`.
- Reuse current NestJS module layering, Prisma repositories/services, Outbox/RabbitMQ, Notification Center, i18n and existing Vue design system components.
- Add pt-BR and en-US translations in the same sprint that introduces UI or user-facing messages.
- Update Swagger/Redoc through DTO/decorator changes for REST APIs.
- Update AsyncAPI only when the event is actually published or consumed.
- Logs, audit and notification payloads must be sanitized and idempotent.
- Frontend must not decide authorization; backend remains the source of truth.

## Sprint MP-1 — Automatic Token Refresh Lifecycle

**Branch:** `feature/10.2-mp-1-token-refresh`
**Status:** implemented.

Goal: make Mercado Pago operations safe under normal token expiration.

Scope:

- Add a `MercadoPagoCredentialManager` or equivalent service.
- Decrypt credentials only in memory.
- Refresh when token expires within the threshold, initially `now + 10 minutes`.
- Use a distributed lock per `GatewayConfiguration`.
- Persist rotated refresh tokens safely.
- Add credential versioning or optimistic update guard.
- Mark connection as `REAUTH_REQUIRED`/degraded when refresh is unrecoverable.
- Publish authorized notification `mercado_pago.connection_reauth_required`.

Acceptance:

- Expired token refreshes automatically before create/fetch operations.
- Concurrent operations trigger one refresh path.
- Revoked/invalid refresh token blocks future provider operations and marks reauth required.
- Transient provider/network failure does not immediately mark reauth required.
- Unit/integration tests cover success, lock contention, invalid refresh and transient failure.
- No token is logged, audited, queued or returned.

Implemented notes:

- `MercadoPagoCredentialManager` loads encrypted tenant credentials, refreshes near-expiration tokens with Redis lock `lock:mercado-pago:refresh:{gatewayConfigurationId}`, and writes rotated credentials back as a full AES envelope.
- Gateway orchestration resolves Mercado Pago credentials through the manager for payment creation, payment instructions and cancel/refund calls; non-Mercado Pago providers keep the existing decrypt path.
- Invalid/revoked refresh tokens mark `GatewayConfiguration.status = REAUTH_REQUIRED` and `healthStatus = DEGRADED`, create sanitized audit, and publish `mercado_pago.connection_reauth_required` through the Notification Center when internal producers are enabled.
- Transient refresh failures mark health degraded without changing status to reauth-required.
- OAuth callback now persists encrypted Mercado Pago credentials using the current AES envelope shape.

## Sprint MP-2 — Mercado Pago Webhook Foundation

**Branch:** `feature/10.2-mp-2-webhook-foundation`

Goal: implement a production-safe Mercado Pago webhook endpoint and inbox/outbox foundation.

Scope:

- Implement `POST /webhooks/mercado-pago`.
- Validate signature when configured.
- Persist inbox using existing `WebhookInboxEvent` or a minimal extension.
- Derive idempotency from provider event id/resource id before payload hash fallback.
- Publish `mercado_pago.webhook_received`.
- Respond quickly and process asynchronously.
- Resolve tenant only through safe mappings: merchant id/configuration, existing payment, external reference or known tenant-scoped mapping.

Acceptance:

- Mercado Pago dashboard test webhook can be received.
- Invalid signature is rejected in production.
- Missing secret is allowed only in non-production with an explicit warning policy.
- Duplicate webhook does not create duplicate processing.
- Unknown tenant/resource does not attach to an arbitrary tenant.
- Logs store hashes/sanitized metadata, not raw sensitive payload.
- AsyncAPI includes only events implemented by the sprint.

## Sprint MP-3 — Payment Status Sync

**Branch:** `feature/10.2-mp-3-payment-status-sync`

Goal: make Mercado Pago-created payments operational after creation by syncing provider status through webhook/fetch.

Scope:

- Fetch full payment details from Mercado Pago workers when webhook data is only a trigger.
- Locate internal `Payment` by provider payment id, external reference or tenant-safe mapping.
- Map statuses consistently:
  - `approved`/`accredited` → `APPROVED`
  - `pending`/`in_process` → `PENDING` or `PROCESSING` according to existing policy
  - `rejected` → `FAILED`
  - `cancelled` → `CANCELED` if enum supports it, otherwise existing failure policy
  - `refunded` → `REFUNDED`
  - chargeback → event/case instead of inaccurate status when enum lacks representation
- Emit audit/payment events and authorized notifications only on meaningful transitions.
- Add replay support for inbox/outbox event reprocessing where current tooling allows it.

Acceptance:

- PIX/boleto can move from pending to approved through webhook processing.
- Duplicate webhook does not duplicate audit or notifications.
- Terminal status does not regress unless explicit policy allows it.
- Provider status/detail is stored sanitized.
- Tests cover approved, failed, refunded/chargeback trigger and unknown tenant/resource paths.

## Sprint 9B-3 — Mercado Livre x Mercado Pago Matching

**Branch:** `feature/10.2-9b-3-ml-mp-matching`

Goal: match Mercado Livre orders, LedgerFlow payments and Mercado Pago financial events.

Scope:

- Match by provider payment id first, then external reference/order id, then report ids.
- Amount/date matching can create candidates only, never final auto-reconciliation.
- Create settlement cases with explicit statuses and divergence types.
- Send divergences to fine mesh/manual review.
- Audit every manual resolution.

Acceptance:

- Exact id match can auto-reconcile.
- Candidate-only matches require manual confirmation.
- Divergences appear in fine mesh with evidence.
- Manual resolve/ignore/reopen is append-only and audited.
- No settlement case crosses tenant boundaries.
